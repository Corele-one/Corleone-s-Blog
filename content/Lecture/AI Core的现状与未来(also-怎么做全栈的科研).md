## 二、AI Core 典型架构（LPUv1）

在讨论问题之前，先理解 AI Core 的典型架构。以 LPUv1 为例，其核心由以下功能单元构成：

![[file-20260718151412959.png]]

| 功能单元 | 职责 |
|---------|------|
| **Cube** | 矩阵乘法，AI Core 的算力主力 |
| **Vector** | 可配流水线，支持单目、双目、规约、广播、reshape |
| **Scalar** | 计算地址、控制流、管理依赖关系 |
| **xDMA** | 各级存储与片外之间的显式数据搬运 |
| **LMB/RMB/PSB/PMB** | 存储左矩阵、右矩阵、结果矩阵、参数 |
| **Unified Buffer** | 用于 Vector 和 Cube 之间的数据交换 |

计算单元和数据搬运单元构成独立流水线，在 Scalar 的调度下配合工作。

### 执行模型：串行、并行、流水、同步

各功能单元并行运行，Instruction Scheduler 通过 `set_flag` / `wait_flag` 机制管理数据依赖：

![[file-20260718151632084.png]]

- `set_flag`：通知下游可以开始
- `wait_flag`：等待上游完成

这套同步机制保证了 Cube、Vector、GDMA、LDMA 等单元之间能够正确地流水与协作。

### 性能建模

一个 Layer 的执行时间可以近似为：

$$T_{layer} \approx \max(T_{cube},\; T_{vector},\; T_{memory}) + T_{reorder} + T_{scalar} + T_{sync} + T_{tail}$$

![[file-20260718151739106.png]]

在 CNN、RNN、LSTM 时代，主流工作负载整体呈现计算密集特征，$T_{cube}$ 往往占主导——只要持续堆高 Cube 算力、把矩阵计算做快，整体性能通常就能随之提升。然而，LLM 时代打破了这个假设。

### 算子级快速性能建模

为了快速评估算子性能，可以采用基于**生产者-消费者模型**的性能建模方法：

![[file-20260718151811278.png]]

- **指令级建模**：单指令执行时间分解为 $t_{head}$、$t_{body}$、$t_{tail}$，其中 Head、Body、Tail 都是对微架构的抽象；
- **算子级建模**：在指令级建模基础上，建模指令的四个关系——串行、并行、竞争、依赖；
- **优势**：运行速度接近功能模型，同时保留了关键微架构细节。

## 三、大模型时代的新需求与现有 AI Core 的四大错配

LLM 的工作负载与传统 CNN/RNN 有本质差异。算子构成与访存模式发生了根本性转变：

![[file-20260718151944496.png]]

| 维度 | 传统模型（CNN/RNN/LSTM） | LLM |
|------|--------------------------|-----|
| **算子特征** | 以大块 GEMM/卷积为主 | Decode 阶段 GEMV 占主体，非矩阵算子（量化等）占比显著增加 |
| **访存模式** | 单算子计算量大、访存规则 | MoE、Paged Attention 造成访存离散 |
| **瓶颈** | $T_{cube}$ 主导总时延 | 端到端吞吐取决于 Cube/Vector 交互、量化、离散访存、控制调度的综合效率 |

这带来了现有架构的**四大错配**：

### 错配一：编程模型复杂度失控

![[file-20260718152126918.png]]

编程模型直接暴露 Cube、Vector、xDMA、Buffer 细节，开发者须逐一手动管理，带来三大负担：

- **Buffer 管理**：UB / LMB / RMB / PSB 各自独立，需手动 ping-pong 编排、手动分配地址、手动配置 Data Layout；
- **异步同步**：Cube-Vector-xDMA 之间靠 set/wait flag 编排，依赖关系稍有遗漏，轻则结果错，重则死锁；
- **跨代重写**：不同代架构、同一代架构不同规格，同一算子需单独开发。

后果：开发新算子难，算子性能调优难（不同 seq_length 优化策略不同），编译器设计空间爆炸。**缺少稳定的虚拟抽象，编程复杂度随模型迭代持续增长。**

### 错配二：低精度数据流未被原生支持

![[file-20260718152242286.png]]

以 MXFP4 为例，低精度数据类型的处理链条为：`load tile → unpack → reorder → scale align → matmul → acc convert → requant / dequant`。

MXFP 的核心思路是：一个小块元素（如 32 个）共享 block scale / exponent，块内元素再用 FP4 / FP6 / FP8 等低位宽表示，用共享 scale 换取更好的范围/精度折中。但存在的问题是：

- **scale 引入额外数据流**：MXFP 格式要求每组 scale 被加载、复用并和对应数据块精确对齐；
- **亚字节位宽与对齐假设冲突**：4 bit / 2 bit 要么按字节存而损失压缩收益，要么紧密打包后每次使用前都要解包，传统 DMA 不擅长处理 packed layout；
- **反量化和累加精度处理打断流水**：浮点数 matmul 通常用 FP32 累加，再经过 convert / requant；若未固化成数据流，会带来 Cube 与 Vector 之间的交互停顿。

per tensor 的量化 scale 在不同 tensor 中是不同的，这会引入额外的数据流开销。

### 错配三：结构化离散访存被当随机处理

![[file-20260718152446119.png]]

LLM 中常见的离散访存模式包括：

- **PagedAttention**：逻辑连续的序列，被 page table 映射到离散 block；
- **MoE**：目标地址由 router / index table 决定，行内仍连续；
- **长序列 KV Cache**：KV Cache 被切片。

它们的共同特征是：地址不连续，但可提前推导。然而被当作随机访存处理的代价是：

$$\text{Eff} = \frac{\text{UsefulBytes}}{\text{TrafficBytes}}, \quad \text{TrafficBytes} = \text{TouchedLines} \times \text{LineSize}$$

访存效率降低的瓶颈不在 HBM 峰值，而在 **TouchedLines 被放大**。页表、index、mask 明明可以用于合并请求、复用 line、提前预取，但这些规律信息在当作随机访存处理时被丢弃了。

### 错配四：Scalar 控制流超载

![[file-20260718152614004.png]]

控制复杂度已超出顺序 Scalar 的承受范围，成为复杂模型的卡点：

- **动态 shape**：实际序列长度运行时才定，offset、loop counter、mask 随之变化；
- **稀疏 / MoE**：稀疏索引、router 结果同时决定访问地址与分支走向；
- **通信 / 同步**：通信状态、同步 token 需跨步骤维护与轮询。

顺序 Scalar 的问题在于：无法掩盖延迟（顺序执行无法绕过 cache miss、同步等待或通信延迟）、寄存器溢出（复杂状态太多，spill 到 Dcache 后进一步放大停顿）、动态控制流难适配（shape、mask、路由变化多，静态流水容易失效）。

## 四、AI Core 的演进：面向低精度数据流的设计

面对上述错配，AI Core 的演进方向是：**把量化和解量化放在数据搬运中来做**，而不是在计算单元之后再额外处理。

![[file-20260718153329672.png]]

问题的核心定位是：低精度量化不是给矩阵单元新增一个 dtype，而是引入一条从 Global Memory 到输出的完整数据流，每环节都有独立的带宽、对齐和格式约束。

一个低精度 Tile 应携带：packed layout（打包格式）、scale format / granularity（粒度）、group size（分组大小）、accumulation type（累加精度）、reorder policy（重排策略）。

三个关键工程落点：

1. **scale 专用数据通路**：scale 要与数据一起 load、cache，对齐复用，带宽同等重要；
2. **unpack / reorder 随路到搬运阶段**：由 xDMA 在搬入时完成，不占 Cube/Vector 执行时间；
3. **accumulate / requant 随路到回写阶段**：在 Cube 中增加专用累加、量化单元，不占 Vector 执行时间。

## 五、为什么要做全栈？

### 华为海思的实践

华为海思过去几年，很多能力是被逼出来的：软件栈要自己做，指令集要自己定义，关键 IP 要自己掌握，SoC 集成要自己扛，互联协议要自己推，先进封装、3D 集成、光互联、系统 fabric、AI 芯片、CPU、NPU、内存子系统也都要自己打通。这个过程当然很苦，但苦到最后，会形成一种很特殊的技能点——**全栈的联合调优能力**。

![[file-20260718153535956.png]]

> 韬定理，名义上是提出来一个全局时间的优化目标。**只有在全栈足够可控的时候，优化才做得下去。**
> ——乱序摸鱼（周若愚，华为海思图灵架构部，Ascend 核心架构师之一）

### 个人为什么也要追求全栈

团队的要求是：不仅团队要形成全栈能力，而且个人也要形成全栈能力。

![[file-20260718153622585.png]]

全栈能力带来的四个好处：

1. **设计质量好**：能判断一个特性该放在推理框架、算子、架构、ISA 还是微架构，所有设计决策都有全局视野，层次划分、模块划分、接口定义更清晰；
2. **抓虫效率高**：验证阶段发现问题，快速定位到底是算子还是 RTL 的问题，不需要跨团队讨论；
3. **创新能力强**：创新来自于信息的排列组合，知道的信息越多越容易产生 idea；
4. **沟通成本低**：每个人都知道每一个设计的需求来自哪里，不会鸡同鸭讲。

## 六、怎么做全栈的科研：方法论

### 造火箭原理：做一件事，凑齐让事情发生的要素

![[file-20260718153852387.png]]

发好文章的要素和找到好工作的要素本质上是相通的：

| 发好文章 | 找到好工作 |
|---------|----------|
| 对一个领域有深入的理解 | 扎实的工程能力 |
| 发现有工作的问题 | 良好的表达能力 |
| 提出解决方案 | 缆密的逻辑思维 |
| 实现并验证解决方案 | 演绎、抽象、系统思维 |
| 将解决方案表达出来 | 流片与实习经历 |

基于这套理论，培养路径是：

1. **带学生完整做一遍 NPU 全栈**：深入理解 NPU，培养工程能力、逻辑思维、演绎、抽象能力；
2. **针对 NPU 性能瓶颈**：做调研、提方案、做验证；
3. **发表论文**：进一步提升表达能力、逻辑思维能力。

### 金字塔原理 Pro：需求为纲、分解归纳、划分层次、以上统下

![[file-20260718153943745.png]]

这是做全栈科研的核心方法论：

- **需求为纲**：做任何事情之前都想清楚自己的需求是什么。需求是逐级分解并细化的，需求将不同层次串联起来；
- **分解归纳**：分解——一级模块有多个需求，明确每个需求如何由多个二级模块共同实现；归纳——总结每个二级模块承接的需求再继续分解；
- **划分层次**：需求是逐级分解的，每分解一次形成一个层次。明确要做的事情在什么层次，以及在这个层次要解决的问题；
- **以上统下**：愿景决定战略，战略决定战术，需求决定实现，目的决定行动。没把高抽象层次的事情定下来之前，不急于做低抽象层次的事情。

> 怎么承载复杂度，你做过最复杂的项目是什么？——这就是一个承载复杂度的方法论。

### 算力-算法-数据三角理论：三者有其二才能做好事情

![[file-20260718154239703.png]]

三要素分别对应什么：

| 要素 | 含义 |
|-----|------|
| **算力** | 学习能力、理解能力 |
| **算法** | 做事逻辑、思考框架、方法论 |
| **数据** | 项目经验、踩坑记录、案例证据 |

为什么不会让 junior 开拓新研究方向？因为 junior 只有算力，还没有算法与数据。三者只占其一，大概率失败，无法进入正反馈，持续的挫败感，科研之苦大都源自于此。

培养流程：先灌算法（讲造火箭原理和金字塔原理 Pro），再灌数据（手把手带着做项目、搞科研，边做边讲如何把方法论用到实践），最后放手让其自主研究（方法论内化、实践数据积累足够后，再放手独立开方向）。

### 研发体系：完全按照工业界标准

![[file-20260718154402056.png]]

团队的研发流程完全按照工业界 NPU 研发标准来走：

**收集需求 → 定义架构 → 定义 ISA → 电路方案 → RTL 编码 → UVM 验证 → FPGA 集成**

同时并行走推理框架、功能模型、性能模型、性能校准。

| 角色 | 核心职责 | 角色 | 核心职责 |
|-----|---------|-----|---------|
| Architect | 架构 / ISA | Project Leader | 项目管理、团队协调、解答新同学问题 |
| System Engineer | 电路方案、验证方案、推理框架方案 | Model | 算子、功能模型、性能模型 |
| Design | RTL 编码、FPGA 综合 | Software | 大模型推理，产出处理结果 |
| Verification | UVM 环境、构造测试用例、收集覆盖率 | Infra | GitLab 平台、VCS 环境、CI、AI 工具、Claw |

## 七、小结与个人思考

本次 Tech Report 围绕 AI 芯片架构设计方法论展开，几个关键 takeaway：

**入门路径**：学习架构最快的方法是”自己推一遍”——先动手设计和实现，再对比参考，而非单纯模仿。例如，先写算子来理解指令集，再理解微架构。认知是自下而上的，应先从具体的电路方案和 RTL 代码入手，理解其工作原理，再逐步构建对整个系统的宏观理解。

**架构设计核心原则**：架构设计应始于明确的业务需求和功能规格，先定义整体架构、模块划分和工作流程，再在此基础上定义指令集（ISA）。验证流程也应遵循自下而上的逻辑，从单条指令到完整算子逐步推进。

**AI 对行业的影响**：AI 难以取代具备强大架构设计能力和逻辑思维能力的人。未来的核心竞争力在于解决复杂问题的顶层架构能力。在校期间应尽可能追求全栈能力，深入理解从推理框架到硬件的各个环节。

**性能建模细节**：指令集建模关注单条指令的执行时间，而算子集建模则要考虑多条指令并行、串行、依赖等复杂情况下的总执行时间。性能模型的保真度难以保证，通常需要在最终阶段通过对比 C++ 模型和 RTL 进行性能校准。当前硬件设计通常采用”解量化-计算-再量化”的模式，直接计算量化数据的可行性需要深入研究硬件实现细节。
