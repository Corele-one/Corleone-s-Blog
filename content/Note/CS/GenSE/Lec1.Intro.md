# 1. 我们站在重要的交叉路口

![[file-20260829130853981.png|500]]

> 我的笔记
>
> 技术的革命把昂贵的能力变成了日用品

这不是“机器又强了一点”，而是能力突然从稀缺品变成日用品。老师把 PC、互联网、移动互联网与 ChatGPT 放在同一条线上：前几次变化都降低了使用某种能力的门槛，并重写了人们的生活和工作方式；生成式 AI 也正在发生同样的事。

- 课堂用早期 QQ/OICQ 的例子说明互联网如何突然让人接触到遥远世界；又用菜场的二维码说明移动互联网如何在很短时间里改变日常行为。
- ChatGPT 在 2022 年出现后迅速成为人类历史上增长最快的一类产品。今天的课程不假定我们已知道答案，而是要在断点刚发生时做实验。

> ==真正的拐点，不是机器又强了一点；而是某种昂贵能力，突然变成了日用品。==

## 作业完成了，学习发生了吗？

![[file-20260829130851504.png|500]]

Vibe coding 让“把作业链接交给 Codex”成为现实，甚至不必复制粘贴。老师用操作系统课实验举例：过去困难的实现过程本身会形成训练；若教师用 AI 出题、学生用 AI 交付，闭环里反而可能只有学生没有获得训练。

这里的结论不是简单的“该学”或“不该学”。手工编码的稀缺性会下降，但理解、建模、验证和驾驭工具的能力更重要。**同一份成品已经不再能可靠地证明同一种能力。**

## AI 时代，大学还教什么？

![[file-20260829131651741.png|500]]

> 我的笔记
>
> 人和AI的区别：
> 信息差
> 能坐牢
> **能驾驭**

老师把大学仍应训练的能力概括为三层：

- **信息差**：知道什么可靠、哪里未知、该向谁或向什么工具求证。
- **能坐牢**：不是鼓励吃苦，而是能承受探索、失败和长期反馈，不只追逐一次性得分。
- **能驾驭**：让人、Agent、工具和反馈持续对齐目标；能定义边界、分配责任、检查结果。

火星气候探测器的单位换算事故提醒我们：风险常常发生在团队与系统的接口处。工程能力不只是“局部做对”，还包括让错误能被发现、追溯和停止。

## 这门课准备怎样上

课堂不是把一套固定答案“直播一遍”。老师把现场教学看成一次带有即兴成分的表演：先用讲义约束主线和例子，现场与同学互动；课后再回看录像，修正不恰当的例子、切片并精修内容。因此，现场版可以不是最优版，**可维护的内容链路**才是课程的长期形态。

- 对“听课型”同学，老师明确建议优先使用课后整理过的材料；现场的价值更偏向讨论、反馈和共同实验。
- 课程希望以项目和可访问的成果为导向，而不是只用一次分数区分人。最终更有意义的交付，是简历上能打开、能运行、能解释的作品链接。
- Token 自费不是鼓励无节制消耗；课堂演示会尽量采用足够便宜、响应足够快的模型，让每个人先获得一手的成本—质量—延迟感受。
- 仍要承认现实约束：GPA／考试在短期内存在，容易诱发 reward hacking；但它们不应成为大学训练的唯一目标。

# 2. Everything is Code：把过程留下来

![[file-20260829132358169.png|500]]

> 我的笔记
>
> **Slides的生成**:
> 迭代过程中用不同的提示词来做slides，然后用另外的一个agent来盲评、review。3个subagent赋予不同的personality分别干不同的事情，**实现算力换智力的这样一个过程**
>
> *Everything is Code.*

老师展示这套 slides 的生成方式：文本是 **source of truth**，在完整讲义中选定上下文和边界，交由 Agent 扩写，再生成 Markdown slides，由浏览器渲染。图片、网页和视频片段被统一标记为 AIGC；逻辑改变时改源文件，而不是手工修补最终截图。

这也解释了为什么“保存最终图片”不够：真正值得永生的是**可编辑、可 diff、可复现的源代码与构建过程**。一次成功的过程若可以重放、检查、修改，才会成为下一次工作的资产。

> [!tip] 对自己的实践
> 当一个 Agent 任务成功后，不要只保留聊天记录；至少保留输入、约束、脚本／prompt、验证方式和输出位置。==把一次性操作沉淀为可再运行的系统，才是真正的复用。==

![[file-20260829132536280.png|500]]

“没有 token 的 CS 学生应该立即退学”是夸张说法，重点不在 tokenmaxxing。Token 是这个时代的实验耗材：亲自使用，才能形成对成本、质量与延迟的直觉；真正稀缺的是**值得花 token 的问题、清晰约束和可靠验收**。

# 3. LLM 与 Agent：从概率模型到反馈回路

## LLM 的使用者视角

![[file-20260829132823650.png|500]]

> 我的笔记
>
> 实际上就是一个概率分布，这门课是“使用者视角”，不需要任何LLM的知识。

LLM 可以先理解为一个自回归概率分布：

$$P(\text{token}_{t+1}\mid \text{context}_t)$$

它每次给出下一个 token 的分布并采样，输出又会写回 context，因而把静态分布展开为一段计算过程。课程采取使用者视角，不要求掌握模型训练细节；但要记住以下边界：

- “预测下一个 token”是训练接口，**不是能力上限**。模型同时拟合代码、证明、对话和故事，因而压缩了大量世界规律。
- 真正的“编程”对象常常是 **context**：任务描述、已有文件、工具反馈、测试结果、记忆和约束都会改变后续输出。
- 文本流畅只意味着“在当前上下文中像一个答案”，**并不是正确性的证据**。正确性必须由测试、检索、交叉验证或人的判断补上。

![[file-20260829132944248.png|500]]

课堂用“给五岁孩子解释扫描电子显微镜（SEM）”说明 LLM 的另一种价值：它不只检索术语，还能根据听众重编码语言、选择合适比喻，并保留“电子束逐点扫描 → 探测二次／背散射电子 → 信号映射成像素”的因果骨架。把模型用于教学时，不能只满意于比喻好懂；还要检查因果链是否被保留、是否把图像重建误说成直接测量。

![[file-20260831225931890.png|500]]

> 我的笔记
>
> Next-Token Prediction是一个效率很低的计算方式

“next token”也未必是最后的形态。幻灯片提出把 context 视为可写状态：自回归像从左到右用钢笔写作；Diffusion LM 更像先铺开整篇草稿、再多轮去噪并同时修改多个位置。无论模型形态怎样变化，Agent 层已在系统中实现了 context-to-context 的循环：

$$\text{读状态} \rightarrow \text{推理／计划} \rightarrow \text{调用工具} \rightarrow \text{观察结果} \rightarrow \text{更新记忆／状态}$$

所以 Agent 的能力不只来自模型本身，也来自它能否看见状态、做出有效操作、获得反馈并在失败后恢复。

## 从 ChatGPT 到 Agent

![[file-20260829133307322.png|500x280]]

> 我的笔记
>
> 从预测下一个token的概率分布，到发现文本可以接收越来越长的上下文的时候，能否让llm接收不同的Token？——Agent的出现，让llm可以调用CLI工具，把环境的反馈接回模型，实现Coding等多种功能。

Transformer 使计算可扩展，ChatGPT 将能力放进低摩擦的对话界面；reasoning 在测试时投入更多计算；Agent 则把环境反馈接回模型。这条反馈链一旦跨过可用阈值，模型就不只是在回答，而能在 CLI、浏览器、编辑器和服务中完成多步任务。

- ReAct 的“推理—行动—观察”在 2022 年已出现；近年的跃迁还依赖更可靠的模型、长上下文、工具接口与错误恢复。
- 更长的上下文允许承载草稿、算法和过程，但也会带来来源选择、检索和证据综合的新风险。
- 课上将“论文 review”作为例子：让多个具有不同 persona 的 Agent 从不同角度提出观点，再交由主 Agent 讨论、反驳、收敛。这里的“算力换智力”应建立在明确的评价标准上，而不是盲目堆 Agent。

> 我的笔记
>
> ## 一个使用Agent的例子
>
> 如果要review一篇论文，从人类已有的知识开始，看一篇论文里有哪些东西是新的，把这些东西给剥离出来，然后把论文给agent，agent会有不同的personality，会生成出不同的观点，把这些不同的观点再给到主agent，让他们相互讨论直到最后收敛为止——算力换智力。

> [!quote] 使用模型时最容易忽略的一点
> ==模型能补全“看起来合理”的路径，但不会自动暴露未知、分配责任或验证结论。==

# 4. 普通人怎么用 AI：从白板 Agent 到可复用生态

## Agent + 插件：能力由系统共同给出

![[file-20260831232958042.png|500]]

> 我的笔记
>
> **计算机的世界里有什么的概念**

白板 Agent 只是起点。老师强调增强智能早已不是“一个孤立的聪明部件”，而是“人 + 工具 + 语言 + 方法”的系统；可将 Agent 能力粗略看作：

$$\text{Agent 能力} \approx \text{推理} \times \text{可观测性} \times \text{可操作性} \times \text{反馈}$$

只提高其中一项并不够。例如模型再会推理，若看不到真实状态、没有权限操作、操作后也没有反馈，就无法完成可靠的长流程。

### 先用起来，再不断追问

老师给出的入门原则很朴素：**现在就开始用；不知道就随时问 Agent。** 
在一个仓库中，`AGENTS.md` 一类配置会成为模型所见上下文的一部分；与其把 Agent 当作只能接收一次 prompt 的黑盒，不如持续问它“你看到了什么”“为什么这样做”“下一步的风险是什么”。想象力仍是上限，但它必须落在可观察、可验收的环境里。

课上的 Linux 现场系统是一个具体例子：从制作可启动 Debian U 盘、在 QEMU 中验证启动，到配置平铺窗口管理器、终端外观和常用命令替代，老师都用自然语言让 Agent 完成，再要求它检查交付结果。关键不在于人从此无需理解配置，而是先把学习曲线压低：**先得到可工作的系统，再回头复盘它为什么能工作、哪里会失效。**

这也是 Agent 与早期“只回答问题的聊天机器人”不同之处：它会在环境里尝试、失败、观察、再尝试。课堂中 USB 采集卡短暂断开时，Agent 先检查系统设备状态，再以软件方式让设备重新连接；人负责确认视频流是否恢复。这个例子说明，模型输出不是终点，环境反馈才让动作闭环。

![[file-20260831233142651.png|500]]

浏览器不是黑盒。普通人看到像素和按钮；CS 学生还应看到 DOM、协议、事件和状态机。课堂以 Chrome DevTools Protocol 为例：界面背后存在比“点击鼠标”更稳定的控制面。所谓 domain-specific 插件，本质是把巨大、模糊的动作空间压缩成**语义明确、容易验证**的操作。

![[file-20260831233255259.png|500]]

这也解释了“计算机世界里有什么”为什么重要：知道接口、状态、文件、进程、网络请求和权限分别意味着什么，才能判断 Agent 看到了什么、做到了什么、漏掉了什么。AI 时代这种知识不再只是为了手写实现，而是为了**设计更可靠的控制和验收面**。

## 用魔法打败魔法：从操作到资产

![[file-20260831233856617.png|500]]

> 我的笔记
>
> 当Agent走通了一个流程，这个流程中的能力会留下来，可以把操作沉淀成确定性的脚本。
> **自由组合，无限复用**——Linux的Design Philosophy

一个合适的工作流是：先让 Agent 探索页面、理解流程并完成一次任务；再让它把操作沉淀成脚本。它对应 Programming by Demonstration：从一次示范中归纳可执行程序。

- 探路阶段允许花较贵的推理成本；脚本接管后，重复执行接近零成本。
- **demo 成功不等于工程成功**。只有当轨迹可检查、可修改、可重放，才成为软件资产。
- 保存的内容应包括输入、必要状态／权限、操作序列、输出、断言和异常处理，而不只是“它曾经成功过一次”。

课堂还展示了两个“先有半自动、再逐步升级”的个人工作流：

- **邮件处理**：从历史邮件中生成符合个人口吻的回复草稿，将发票等附件归档，再通过待办事项触发后台处理和通知。例行事务可以自动完成；重要邮件仍要由人确认语气、事实和承诺。
- **读书、论文与视频**：先取原文／完整字幕与截图作为 ground truth，再由多个角色从既有知识中剥离“新东西”，给出分层摘要，最后允许人带着原文继续追问。效率的提升来自“减少已知部分的重复阅读”，不是允许摘要脱离原始材料。

> [!warning] 这里的风险
> AI 能把信息摄取和例行执行放大十倍甚至更多，但也会把来源误判、错记记忆和错误承诺一起放大。个人 Agent 必须把**原始材料、自动生成内容、待人工确认的动作**分开保存。

![[file-20260831234008264.png|500]]

> 我的笔记
>
> 信息源——处理系统——有用的知识
> 自举的工作流

当 Agent 走通一个流程，流程中的能力会留下来：网页、B 站、arXiv、Hacker News 等信息源，经处理后再触发下单、上传、归档等操作。接口足够窄且稳定时，各能力可以像 Unix pipe 一样组合。

> [!important] 课堂关键词
> **自由组合，无限复用**。组合的关键不是插件数量，而是接口足够窄、稳定、可验证；工作流也可自举：观察操作 → 发现重复模式 → 自动化 → 回放验证 → 人确认 → 收集新异常。

老师还用 RSS、B 站、arXiv、Hacker News 等信息源举例：信息处理系统并非只靠模型生成内容，而是将可订阅的来源、筛选／总结能力和后续操作接成闭环，再把它们沉淀为 skill 或脚本。

## AI 已来，Harness 未稳

![[file-20260831235235286.png|500]]

能做，不等于能放心托付。若每一步成功率是 $p$，连续 $n$ 步全成功的概率约为 $p^n$：即便单步成功率 99%，100 步也只有 $0.99^{100}\approx36.6\%$。因此长流程必须显式管理：

- 状态与检查点：知道当前走到哪里，断了能从哪里恢复；
- 最小权限：只赋予本任务所需权限；
- 重试与幂等：失败重试不应重复造成破坏；
- 验证与故障恢复：关键结果有独立断言，错误能被定位和回滚。

“稳定、可描述、可验证的重复”，本质上就是一段尚未被抽象出来的程序。Harness 要做的是把这段程序的状态、权限、观测和验收补齐。

# 5. CS Professional 视角：不是拿 Agent 交作业

![[file-20260831235326381.png|500]]

> 我的笔记
>
> **知道编程的能力界限**

CS 学生的优势不只是会写代码，而是理解编程的能力边界：什么可被控制、什么可被观察、什么完成条件可以判定。Agent 的杠杆在于把一次性的自然语言需求转成可重复执行的闭环，而不是代替人放弃理解。

![[file-20260901000140421.png|500]]

> 我的笔记
>
> ## AI在哪里容易犯错
>
> 1. 不要扩大，做最简单的事情不会失败
> 2. 跑出来≠做成，不要上来就对着需求写，容易陷入维护的泥潭
>
> ## 用Agent前，再想想
>
> 用一个新的架构

课堂以“批量统分”说明这一点。流程不是把 140 份试卷丢给模型，而是拆成一个可审计闭环：顶置摄像头在固定位置拍照；离线 OCR 识别学号和各小分并写入文本；人按回车逐张推进，发现摆放异常可立即重拍；第二遍反向核验时，系统朗读姓名、学号和每个小分，人边听边看原卷；脚本而非 LLM 负责求和；最终再写入教务 Excel 模板并抽样检查后提交。

这里的关键分工是：模型／OCR 用于感知，确定性程序用于算术，人工承担异常判断和对每位学生负责的最终确认。能把一件事拆成“该由代码复用”“该由 skill 复用”“仍需人判断”的部分，才是专业能力。

> [!tip] 可编程性的实用判据
> 不要只问“有没有 API”。更应问：是否有**可控输入、可观测输出、可判定的完成条件**？三者具备，即使面对的是浏览器、表格或旧系统，也可能被组织成可靠流程。

![[file-20260901000732768.png|500]]

“让 AI 造航母”仍然会遇到前端、后端、交互、运营与协作的系统性问题。十个环节若各有 90% 可靠，整体约只有 $0.9^{10}\approx35\%$。AI 提高单点产能，并不会自动消除接口和协作风险。

![[file-20260901000946500.png|500]]

少量 prompt 换一个架构，胜过在脆弱方案上不断追加 token。课上的例子强调：目标不是让模型写出一个能跑的长文件，而是设计一个可复用的计算结构——公式／模板和工作表结构保持 $O(1)$，只有数据、计算量和帧数等应随输入按 $O(n)$ 增长。面对“输入从 1 KB 变成 10 KB”时，必须明确哪些东西理应增长；这正是架构检查题。

> 我的笔记
>
> 软件工程研究的是在Gap大的情况下，把一件大事在人和工具的共同协同下做成。

## QRGen 课堂案例：正确结果与可维护架构不是一回事

老师以一个受控的 Excel／二维码动画实验引入软件工程。这里最值得记录的不是它的具体用途，而是两条实现路线的差异：同一个清楚的 specification，Agent 都可能最终“做出来”，但维护成本完全不同。

- **直接实现路线**：模型一拿到需求就输出大量表格公式与特例补丁。即使经过很长时间、最终通过演示，公式中的隐式依赖仍然纠缠；移动一个工作区或增加一个变化，就会触发连锁修改。它在局部“能跑”，却已进入维护泥潭。
- **编译式路线**：先让 Agent 设计一个小型中间表示／DSL，表示异或、拼接等基本操作；再分别把同一份表达式翻译到 Python 和 Excel。Python 端用于验证编码和像素计算，Excel 端负责呈现；每个翻译器和基本操作都有独立校验，最后再生成目标工作簿。

第二条路线并没有减少问题本身的复杂度，却把复杂度放在可验证的边界内：**实现可替换，语义只有一份；局部正确性可以累积为整体可信度。**
这正是“少量 prompt，换一个架构”的含义。

# 6. 软件工程：补上 Intention、Spec 与 Implementation 的 Gap

## 软件工程为何仍是系统工程

![[file-20260831235555796.png|500]]

> 我的笔记
>
> 软件工程是一个**系统性**的工程，任何一个环节不好产品都做不好。

《人月神话》的焦油坑意象说明：大型系统一旦陷入耦合、隐含知识和验证债，新增一点功能也会消耗巨额协同成本。焦油坑不是单纯的代码量；**功能是局部的，约束却是全局的。**
因此即使 AI 能更快产出局部实现，也不能自然解除接口、集成、验收与演化的风险。

![[file-20260901000423715.png|500]]

> 我的笔记
>
> ## 软件工程中的三个空间
>
> **AI上手解决问题的欲望太强了**
>
> Intention(意图)——Spec——Implementation(实现)
>
> 每一种Intention有多种可能的实现，就算是同一个spec也有不同的实现方法，三个空间之间存在一个巨大的gap

软件工程中的三个空间：

| 空间 | 含义 | 课堂中的典型问题 |
| --- | --- | --- |
| **Intention space** | 人真正希望达成的目标，提出者自己也未必 100% 清楚 | “做一个国民级应用”“做点外卖的小程序并挣钱”到底要什么？ |
| **Specification space** | 对功能、架构、设计和约束的可讨论描述 | 用户、流程、边界、性能、安全、数据模型怎样规定？ |
| **Implementation space** | 可运行的、无歧义的程序与配置 | 表怎么拆、字段如何定、选 KV 还是关系型数据库？ |

每个 intention 对应许多 spec，每个 spec 又对应许多实现。$\text{Impl} \models \text{Spec}$ 只说明实现符合规格，并不自动推出规格满足真实意图；测试能够验证前者，却不能替人决定后者。

![[file-20260901000732768.png|500]]

> [!important] 本讲最核心的工程判断
> ==软件工程／Vibe coding 最重要的事情，是补 Gap：既阻止 AI 在大 Gap 中乱猜，又发挥它在边界清楚时从 A 到 B 的能力。==

> 我的笔记
>
> **软件工程/Vibe Coding最重要的事情是补Gap**
> 阻止AI乱猜的同时，发挥AI从A到B的能力

模型补 gap 的方式本质上是猜。小而可逆、影响低的猜测可以先做后验；高影响、难回滚的决策应当先停下来提问或做最小实验。课堂给出的决策式是：当

$$P(\text{猜错})\cdot C(\text{返工}) > C(\text{澄清})$$

就该先澄清，而不是让 Agent 继续生成。

## 别让模型一头扎进泥潭

![[file-20260901001041529.png|500]]

> 我的笔记
>
> **当AI开始产生Slop的时候，投入更多的token只会让AI做的更失败**

模型被训练为在有限 token 内完成任务，天然倾向于“立即遵循指令”。在大决策上犯错后，它未必像有经验的人那样主动方法论重建，于是更多 token 可能只是在错误方向上堆出更多 **slop**。

> 我的笔记
>
> 从Intention到Implementation是一个越来越大的杠杆，越早的时候的Gap越大，在Intention中的微小变化会在Implementation产生更大的变化。
>
> 上了考场上的题目都是要在5min内解决一个问题，本质上和Agent的训练方式是一样的，但是Agent有更大的上下文，能够把这个任务完成的更好。如果没有好奇心想要知道世界是怎么运行的，没有self-motivation就从未训练如何解决long-horizon的问题。

- 不要无边界扩大问题；优先做最小、可验证的事情。
- “跑出来”不等于“做成”：先讨论真正的需求、约束和架构，再写实现。
- 目标不是消灭猜测，而是让猜测显式、可逆、可验证；让错误出现得早、传得不远、回退得便宜。

![[file-20260901001535597.png|500]]

> 我的笔记
>
> ## 失败的定义
>
> 长程信号的Reward

在 LLM 时代，失败的定义没有变：**软件没有满足真实 intention 和 constraints。**
但真实 intention 与真实 spec 难以直接观察，测试和 reward 很多时候只是代理信号（proxy）。通过测试不等于满足真实意图；long-horizon 的 reward 尤其稀疏、延迟且容易被“做题家式”的优化钻空子。

![[file-20260901001736651.png|500]]

> 我的笔记
>
> AI已经被训练成做题家了，AI怎么成为一个好的设计者，训练出好的**工程品味**

工程不是三条孤立技巧，而是反馈控制：

1. **拆解**：把不可控的大赌注拆为小 gap，缩短因果距离；
2. **验证**：用测试、CI、断言和门控限制错误传播；
3. **迭代**：小步提交、快速验证，让噪音尽早暴露。

## 工程品味与人要负责的部分

![[file-20260901001812240.png|500]]

当 AI 逐步接管执行、智能乃至部分设计时，人的稀缺性会向上游迁移。人不应只把自己定位为“亲手生产者”，而要决定什么值得存在、为什么做、为谁做、后果由谁承担。

工程品味不等于“审美好看”，而是能在不完整信息下判断：什么问题值得投入、什么代价不可接受、什么证据足以继续、何时应停止。正当性、问责和最终决策权并不会自动随模型能力增长而迁移。

![[file-20260901001823955.png|500]]

“古法编程”死掉的，是手写实现的稀缺性，而不是理解。边界清楚、上下文装得下、结果可低成本验收的单点任务会越来越属于机器；人的注意力应压在定义问题、设计验收、解释失败和承担后果上。

# 7. 结尾：为什么招你，而不是订阅 AI？

![[file-20260901001917508.png|500]]

> 我的笔记
>
> **为什么我要招你，而不是买一个200$的Claude Max？**

“为什么要招你，而不是买一个每月 200 美元的 Claude Max？”不是要和 Agent 比产能。课堂给出的回答可以压缩为：

> ==我能找到值得解决的问题，把未知拆成便宜的实验，用证据让坏方向及时停下，并对长期结果负责。==

这四件事对应方向、验证、责任，也对应一支可复制的 Agent 团队所不能自动替代的部分：它可以帮助收敛真实结果，但不能自行决定什么是真实结果，更不能在没有授权的情况下承担后果。

## 本讲的行动清单

1. 选一个重复但有边界的个人任务，先让 Agent 做一次，再把成功轨迹沉淀为可重放脚本或 skill。
2. 为该任务写出输入、输出、完成条件、权限边界和至少一个独立验证，而不只写 prompt。
3. 遇到模糊的大任务时，先区分 intention、spec、implementation；在高返工风险处提出澄清问题或设计最小实验。
4. 复盘时不只问“AI 做对了吗”，还要问：它依据了什么？我能否验证？失败时能否定位、恢复并解释？

> [!summary] 一句话带走
> ==生成式软件工程不是让 AI 替我把代码写完，而是把人、模型、工具与反馈组织成一个能在变化和约束下继续活着的系统。==
